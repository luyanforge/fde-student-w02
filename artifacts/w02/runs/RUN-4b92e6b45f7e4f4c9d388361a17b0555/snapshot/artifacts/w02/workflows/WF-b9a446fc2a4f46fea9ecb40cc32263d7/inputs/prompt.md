优先整理访谈者列出的 focus_questions 相关陈述，并保留理解这些陈述所需的背景。
区分客户对现状的说法、个人观点和目标、尚待核实的问题。一个条目尽量只表达一项可核对的主张。
同一个术语在不同角色、时间或范围下可能含义不同，保留原文限定，不自行统一。
若原文只提出问题而没有答案，不把问题改写成已经存在的业务规则。

本轮补充要求：
区分「判断」与「结论」：受访者明确声明是个人看法而非核查结论的，原样标注为判断，不得升格为事实或依据。
区分「个人工作记录」与「公司口径」：受访者声明不能作为公司数据使用的材料，标注其效力边界，不得作为口径来源。
「不掌握」「无法确认」「不归我定」不是同一种回答，保留原文措辞，不合并成「未知」一项。
同一件事由多个角色分别陈述时，逐条保留各自说法与限定范围，不在提取阶段判定谁对谁错。
涉及权限、签批、预算的陈述，注意是否属于受访者本人有权决定的范围内，超出其职权的表述标为待确认。

输出格式的硬性要求：
只输出一个 JSON 对象，顶层只能有 claims 一个键，不得出现 type、properties、required、additionalProperties 等 schema 关键字。
不要复述、不要抄写、不要简介 Schema 本身；收到 schema 说明后直接产出数据。
所有 review 固定为 {"status": "pending", "note": ""}。

证据引用的硬性要求（校验方式：quote 必须能在该 message 的 content 里原样搜到，否则整轮作废）：
quote 必须是该条 message content 中直接复制的一段连续文字，不允许任何改写。
quote 只允许 6 到 25 个汉字，且**不得包含任何标点符号**：逗号、句号、顿号、分号、冒号、问号、感叹号、引号、括号、破折号、省略号一律避开。
quote 不得包含数字、空格、英文和符号；遇到「120 万」「80 万」这类带空格的数字，改引它周围不含数字的短语。
quote 只能取自同一句话之内，不得跨越标点或换行，不得把两处不相邻的文字拼在一起。
取最能支撑该条主张的那个短语，不要为了完整性搬运整句；宁可短，不可改。
一条候选只引用一个 message 里的一段文字；跨 message 拼接一律作废。

对照示例（以下错法在实测中真实发生过，都会被判废）：
原文：至于能不能承诺“识别下降人群”，这属于效果口径，我不替业务确认。
✗ 错误：至于能不能承诺识别下降人群，这属于效果口径（删掉了原文的引号）
✓ 正确：这属于效果口径
✓ 正确：我不替业务确认

原文：会员数我说的是系统全量会员数，120 万，这个数和活跃会员不是同一个口径。
✗ 错误：120万（原文「120 万」中间有空格，去掉即失配）
✗ 错误：会员数我说的是系统全量会员数，120 万（含标点与数字，风险高）
✓ 正确：这个数和活跃会员不是同一个口径
✓ 正确：系统全量会员数

原文：第二，技术核查由我安排，但走谁的签批、要交问题清单还是字段清单、几个工作日能出结论，这些我现在不作承诺。
✗ 错误：技术核查我可以安排（把「由」改成「可以」）
✗ 错误：几个工作日能出结论，我现在不作承诺（漏掉原文的「这些」）
✓ 正确：这些我现在不作承诺
✓ 正确：技术核查由我安排

message_id 也必须核对（实测有候选把相邻消息的 id 写错，导致整轮作废）：
填写的 message_id 必须是 quote 那段文字真正所在的那一条 message，不能是同一场访谈里相邻的另一条。
同一位受访者连发两条、或一问一答紧挨着时最容易写错；写完 quote 后回到原文，确认这段文字所属的 id 就是所填的 id。
一种自检写法：先定位「这段文字出现在哪条消息里」，再抄那条消息的 id；不要先填 id 再找文字。
反例：MSG-02867 里才有「活动要求不清楚时」，MSG-02869 里没有这段文字；把它记到 MSG-02869 上即为错。

每条候选输出前做一次逐字比对：把 quote 拿到原文里用查找的办法过一遍，搜不到就缩短重写，不允许「大致意思对」的引用。
